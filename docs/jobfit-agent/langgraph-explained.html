LangGraph,
explained

It is a state machine for LLM work. There are four ideas — state, node, edge, reducer — and one design decision that matters more than all of them: the graph drives, the model only fills in blanks.

1

State

the shared folder that travels through the run

One dictionary passes through every step. Steps don't call each other and don't pass arguments — they all read and write this one object. You declare its shape up front:

class JobState(TypedDict, total=False):
    job: dict          # filled by load_job
    fit: dict          # filled by fit_analysis
    plan: dict         # filled by cv_planner
    critique: dict     # filled by critic
    iterations: int    # how many times round the loop
2

Node

one step — just a function

A node takes the state and returns only the keys it changed. LangGraph merges them in. There is nothing special about a node: it can call a model, read a database, or fetch a page.

def critic(state) -> dict:
    data = ask_the_model(...)
    return {"critique": data}   # only this key. job and fit are untouched.

In your agent load_job is a node and it never touches a model — it is a SQLite read. no AI

3

Edge

what runs next — and the one thing a pipeline cannot do

A plain edge is fixed wiring:

graph.add_edge("fit_analysis", "cv_planner")      # always go here

A conditional edge hands the decision to a function — and that function may point backwards:

def route_after_critic(state) -> str:
    if state["critique"]["ok"] or state["iterations"] >= 3:
        return "finish"
    return "cv_planner"        ← backwards. this is the loop.

graph.add_conditional_edges("critic", route_after_critic,
                            {"cv_planner": "cv_planner", "finish": "finish"})

This backwards edge is the whole reason to use LangGraph. A normal pipeline runs A→B→C once. Here the plan goes back for revision — and the exit is a counter you control, not the model deciding it is finished.

4

Reducer

who wins when two nodes write the same key at once

Sequential nodes just overwrite. But your five research topics run at the same time, and all five write topics. LangGraph refuses to guess which wins — so you say how to combine them:

class CompanyState(TypedDict, total=False):
    topics: Annotated[dict, merge_dicts]      # merge both
    costs:  Annotated[list, operator.add]    # append, never replace

operator.add on costs is how the cost line at the bottom of your report accumulates 12 calls from branches that never met.

These nodes really do run on different threads — which is exactly where two of the bugs in this project came from: a SQLite connection and an HTTP session shared across them.

So where is the LLM?

This is the design decision worth defending in an interview.

The common way — model drives

“ReAct agent”. You hand the model tools and it decides: I'll search… now fetch… now I'm done.

  • Flexible, can improvise
  • Can loop forever
  • Can skip steps or call the wrong tool
  • Hard to unit-test — behaviour is the model's mood

Yours — graph drives chosen

The model never chooses the next step. It is called inside a node, fills one schema, and hands control straight back.

  • Flow is ordinary Python — testable
  • Loops bounded by a counter
  • Exactly 5 research topics, never a sixth
  • Every node testable with a fake model
The whole model call, inside a node:

fit, usage = models.get_llm("fit_analysis").run(FitAnalysis, system, user)
             │                                 │
             │                                 └─ a schema it is CONSTRAINED to
             └─ ollama:qwen3:4b  or  anthropic:claude-haiku-4-5  (one config line)

It returns a FitAnalysis object. It does NOT decide where to go next —
route_after_critic() does, and that is a function with a unit test.

What that bought, in the real run

Because the graph decides…What actually happened
the loop has a counterstopped after 3 passes — the model never approved, and that was fine
topics are nodes, not choicesexactly 5 ran; the model could not invent a sixth
the model sits behind one seam72 tests in 5 s with a fake model — no Ollama, no network
a node failure is locala schema the model could not fill cost that section, not the run
state is checkpointeda stopped run resumes mid-graph with --resume

The honest trade-off: this agent cannot improvise. If a company needed a different kind of research, it would not invent one — you would add a node. For a job-fit tool that is the right call. For open-ended research it would not be.
